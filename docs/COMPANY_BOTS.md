# Боты для каждой компании (multi-tenant bots)

Дизайн перевода Telegram-ботов из «один глобальный бот на платформу» в «свои боты у каждой
компании». Документ фиксирует согласованные решения и план внедрения по фазам.

## Зачем

Сейчас на платформе по одному `client-bot` и `manager-bot`, оба прибиты к единственному
`TELEGRAM_BOT_TOKEN`. Компания клиента определяется **не при входе**, а в момент `claim`
менеджером: клиент пишет глобальному боту → создаётся с `companyId = null` в общий пул →
менеджер компании X жмёт «Взять» → клиент и его документы/сообщения наследуют `companyId`
менеджера (`conversations.service.ts::claimByManagerTelegram`).

Цель — чтобы у каждой компании был **свой бот** (лицо перед её клиентами и собственный
менеджерский канал), а компания клиента была известна **сразу** из того, какой бот получил
апдейт.

## Принятые решения

| Развилка | Решение |
|---|---|
| Может ли один человек быть клиентом нескольких компаний | **Да, независимо в каждой.** Клиент = пара `(companyId, telegramId)`: отдельный баланс, история и документы в каждой компании. |
| Какие боты делаем per-company | **Оба** — и `client-bot`, и `manager-bot`. Полная изоляция и брендинг. |
| Как заводятся боты и где хранятся токены | **Self-service в админке.** Токен вводится в админке, хранится в БД (шифрование на уровне приложения), бот поднимается динамически без передеплоя. |

Невыносившиеся на обсуждение решения (выбраны по умолчанию): один процесс с реестром ботов
(не под-на-компанию), long polling как сейчас (webhook — оптимизация на потом), `companyId`
в payload очередей (имена очередей остаются глобальными).

## Модель данных

### Клиент = `(companyId, telegramId)`

- `telegram_users`: снять глобальный `unique` с `telegram_id`; `company_id` сделать `NOT NULL`;
  добавить композитный `UNIQUE (company_id, telegram_id)`.
- Один человек = N строк `TelegramUser` (по одной на компанию), у каждой свой `BillingAccount`
  (это уже заложено комментарием к `billing_account_id` — «под будущее компания + сотрудники»).
- Legacy-клиенты из общего пула (`company_id = null`) бекфиллим в дефолтную компанию
  `00000000-0000-0000-0000-000000000001` (`DEFAULT_COMPANY_ID`). После бекфилла `null` не
  остаётся — иначе из-за `NULL != NULL` композитный unique пропустил бы дубли.
- `register` / `resolveClientOrThrow` резолвят по паре, а не по одному `telegramId`.

### Токены ботов в `companies`

К `companies` добавляются (на каждый из двух ботов): зашифрованный токен, кэш `username`,
статус. Шифрование — AES-256-GCM, ключ из env `BOT_TOKEN_ENC_KEY`. Токен — это секрет в БД,
поэтому наличие ключа шифрования обязательно (без ключа шифрование/расшифровка бросают ошибку,
а не молча хранят plaintext).

Поля (рабочие имена): `client_bot_token_enc`, `client_bot_username`, `manager_bot_token_enc`,
`manager_bot_username` (все nullable; компания без заведённого бота — норма, обслуживается
дефолтным ботом).

## Архитектура процессов: реестр ботов

`client-bot` и `manager-bot` из синглтона превращаются в процесс с реестром `Map<companyId, Bot>`:

- Текущая настройка middleware/handlers выносится из `BotService` в фабрику
  `buildBot(companyId, token)`. Хендлеры уже stateless относительно токена — фабрика добавляет
  один middleware `ctx.companyId = companyId`, и все хендлеры читают компанию из контекста.
- Реестр на старте грузит список ботов из api (`GET /internal/bots?kind=client|manager`,
  X-Internal-Key, отдаёт расшифрованные токены — боты в БД не ходят, правило проекта соблюдено)
  и поднимает по `Bot.start()` на каждый. Polling сохраняется (несколько `getUpdates`-лупов).
- Динамика без передеплоя: при сохранении токена в админке api валидирует его через `getMe`
  (сразу получаем `username`), кладёт зашифрованным и шлёт Redis pub/sub событие `bot.upserted`;
  реестр поднимает/перезапускает нужный `Bot`. Для надёжности — периодический реконсайл реестра
  с api (на случай пропущенного события).

Дефолтная компания усыновляет текущий env-токен: пока у компании нет своего токена в БД, для
неё (и для дефолтной) используется `TELEGRAM_BOT_TOKEN` из env. Это сохраняет работу без
регрессий на время внедрения.

## Маршрутизация очередей

Имена очередей остаются глобальными (`client-bot-outgoing`, `manager-notifications`), но в
payload добавляется `companyId`:

- `client-bot-outgoing`: `OutgoingHandler` берёт `registry.get(job.companyId).api.sendMessage(...)`
  вместо единственного `tgApi`. Ответ менеджера уходит клиенту через бот именно его компании.
- `manager-notifications`: `NotifyHandler` так же выбирает Api нужного manager-бота; продюсер
  (`ManagerNotifyService`) проставляет `companyId` и резолвит адресатов **внутри компании**.
- Redis-состояние client-bot: ключ `client-conv:<chatId>` → `client-conv:<companyId>:<chatId>`
  (один человек в ботах двух компаний имеет одинаковый `chat.id` — иначе коллизия состояния).

### Фикс резолва адресатов (нужен в любом случае)

`resolveManagers` (`manager-notify.service.ts`) сейчас при отсутствии назначенного менеджера
делает broadcast **всем** привязанным менеджерам платформы без фильтра по компании — это
tenant-leak. Должен фильтровать по `companyId` клиента.

## Затронутые соседи

- **Кабинет (`client-bff` + `client-web`)** — Telegram Login Widget верифицирует подпись токеном
  `client-bot` (`TelegramAuthService`). Раз `client-bot` теперь per-company, то и виджет/верификация
  per-company: кабинету нужно знать, от какой компании логинится клиент. **Вынесено за рамки
  первой итерации** — кабинет временно остаётся на дефолтном боте.
- **`manager-link`** — deep-link менеджера строится через глобальный `MANAGER_BOT_USERNAME`;
  станет username manager-бота компании (из `Company`).
- **bot-links / identity** — per-company username хранится в `Company` (резолвится при вводе
  токена), поэтому глобальный механизм `bot-link:client|manager` упрощается до чтения из `Company`.
- **Landing** — общий, CTA ведёт на дефолтного бота; per-company лендинги вне рамок.

## Фазы внедрения

0. ✅ **Фундамент данных.** Миграция `telegram_users` (композитный ключ + бекфилл в дефолтную
   компанию), поля токенов/username в `companies`, сервис шифрования секретов (`SecretCipher`).
   Без поведенческих изменений.
1. ✅ **Реестр + маршрутизация (без UI).** Реестр `BotRegistry` в обоих ботах, фабрика
   `configure(bot, companyId)`, `companyId` в контексте и в payload очередей, фикс
   `resolveManagers` по компании, `GET /internal/bots`. Работает дефолтная компания с текущим
   ботом — регрессий нет.
2. ✅ **Self-service в админке.** Управление токенами на странице компаний (`PUT/DELETE
   /companies/:id/bots/:kind`, валидация `getMe`, шифрование, статусы); Redis pub/sub
   (`bot-config-events`) → динамический подъём/перезапуск/остановка ботов + периодический
   реконсайл; deep-link менеджера через username manager-бота компании.
3. ✅ **Определение компании при входе.** client-bot передаёт `ctx.companyId` в `register`, api
   резолвит клиента по паре `(companyId, telegram_id)`; claim больше не наследует компанию —
   только проверяет, что менеджер той же компании, что и клиент (broadcast и так адресован им);
   Redis-ключ состояния client-bot префиксован компанией (`client-conv:<companyId>:<chatId>`).
   Минорный остаточный долг: `updateLanguage` обновляет язык по одному `telegram_id` во всех
   компаниях клиента (NB-комментарий в `language.handler`); метод `assignCompanyToClientDocs` стал
   неиспользуемым (claim больше не переносит компанию) — отдельная задача на удаление.
4. ⏳ **Кабинет per-company** (отдельно, если потребуется).

## Открытые вопросы / долг

- Тенант-скоуп `BillingAccount.companyId` при claim (отмечен как долг в коде entity).
- Контур discovery-агента лидов параметризовать компанией при втором провайдере
  (см. комментарий к `DEFAULT_COMPANY_ID`).
- Кабинет per-company (Фаза 4).
